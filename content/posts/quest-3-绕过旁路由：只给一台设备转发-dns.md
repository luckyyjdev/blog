# Quest 3 绕过旁路由：只给一台设备转发 DNS

之前为了让 Quest 3 正常使用旁路由上的 OpenClash，我直接把主路由的 IPv6 关了。办法有效，但不太合理：家里这么多设备，没必要因为一个头显让全家都放弃 IPv6。

所以这次我把 IPv6 重新打开，准备只解决 Quest 3 的问题。

起因很简单。我在测试 DNS 时发现，同一个域名直接向旁路由查询，返回的是 OpenClash 的 Fake-IP（198.18.0.62）；但 Quest 3 自己解析出来的却是正常公网 IP。我明明已经给 Quest 手动设置了旁路由 DNS，它为什么还会跑去问主路由？

折腾一圈后找到原因：问题不在 OpenClash，而是 IPv6 又给 Quest 开了一条新网络通道。之前关于 Quest 3 网络问题的排查记录，算是这次的前情提要。

<!--more-->

## Quest 的 IPv6 配置从哪来

先介绍家里的网络。主路由是小米 BE6500 标准版（RN02），IP 为 192.168.28.1，负责拨号和家庭网络。旁路由是 NAS 虚拟机里的 ImmortalWrt，地址 192.168.28.2，运行 OpenClash。Quest 3 连接家里的 Mesh 节点，IPv4 地址手动设置，网关和 DNS 都指向旁路由 .2。

我先在关闭 IPv6 的情况下检查头显网络配置。通过 ADB 可以看到，Quest 的 Wi-Fi 接口虽然有一个 `fe80::` 开头的 IPv6 地址，但没有 IPv6 默认路由，也没有 IPv6 DNS。这种地址属于链路本地地址，有它不代表设备已经能访问 IPv6 公网。此时 Quest 的 DNS 查询确实都能拿到旁路由返回的 Fake-IP。

接着我重新打开主路由的 IPv6，问题就出现了。Quest 不仅拿到了公网 IPv6 地址，还自动获得了一套 IPv6 网关和 DNS。原来的 IPv4 设置没变，只是多出来一套：

```text
Quest 3 → Mesh 节点

IPv4 默认网关 → OpenWrt .2 → OpenClash
IPv4 DNS      → OpenWrt .2

IPv6 默认网关 → 主路由 .1 → 公网
IPv6 DNS      → 主路由 .1
```

IPv4 还按原来的设置走旁路由，但 IPv6 已经直接交给主路由了。也就是说，即使我把 IPv4 DNS 设成旁路由，也不代表 IPv6 的 DNS 查询会经过旁路由。

为了确认，我用 ADB 查了 Quest 的 IPv6 路由：

```bash
adb shell ip -6 route show table all
```

又查看了 Wi-Fi 接口的邻居表：

```bash
adb shell ip -6 neigh show dev wlan0
```

结果发现，IPv6 默认路由对应的 MAC 地址就是主路由的 MAC。我还从 Quest 直接访问了一个公网 IPv6 数字地址，能正常收到响应。这说明问题不只是 DNS：Quest 的 IPv6 网络本身就直接走主路由。即使后面把 DNS 修好，也不会自动让 IPv6 流量经过 OpenClash。

那 Quest 的 IPv6 DNS 又是从哪来的？继续抓包后找到了原因：主路由在发送 IPv6 路由通告（RA）时带上了 RDNSS 信息，相当于主动告诉局域网设备“你们可以用我的这个 IPv6 地址作为 DNS 服务器”。它公布的正是自己的链路本地地址。虽然小米路由器后台显示已经从运营商获取了上游 DNS，但 Quest 实际拿到的 DNS 地址是主路由自己。主路由同时也开了 DHCPv6，不过这次抓到的 RA 已经足以解释 DNS 地址来源。相关资料可以参考 IPv6 邻居发现协议和 RA 中的 DNS 配置（RDNSS）。

## 旁路由本身没问题

找到问题后，我又检查了一遍旁路由。最初怀疑的是 ImmortalWrt 没有正确监听 IPv6 DNS，或者 OpenClash 的 IPv6 配置有问题。但 SSH 上去检查后发现，旁路由上的 dnsmasq 本来就支持 IPv6，TCP 和 UDP 的 53 端口都在正常监听，而且能把查询交给本机 OpenClash。我还找了一台电脑，直接向旁路由的 IPv6 地址发起 DNS 查询，返回的依然是 Fake-IP。

所以旁路由本身没问题，只是 Quest 的这部分查询没有发给它。

有个容易混淆的点：当时旁路由没有配置 IPv6 上游默认路由，OpenClash 的 IPv6 流量接管也没有开启，Mihomo 的 `dns.ipv6` 同样是关闭的。但 `dns.ipv6` 主要影响 DNS 是否返回 AAAA 记录，并不意味着它不能通过 IPv6 接收 DNS 查询。通过 IPv6 发过来的 DNS 请求，完全可以正常返回一个 IPv4 的 A 记录。这一点可以参考 Mihomo 的 DNS 配置说明。

既然旁路由没问题，接下来就要让 Quest 的 DNS 重新走回旁路由。我想过几个办法：

- 让 Quest 单独使用 IPv4。
- 给需要代理的设备单独划分一个双栈网络。
- 直接修改主路由 DNS 配置，让所有设备都使用旁路由。

这些办法都有各自的问题。家里没有多余网口和 AP，现有 Mesh 也没验证过能不能把某个 Wi-Fi 单独绑定到 VLAN。小米路由器后台的 DNS1、DNS2 是 WAN 上游 DNS 设置，我没找到按设备单独发布 IPv6 DNS 的入口。让全家都使用旁路由 DNS 我更不愿意：现在其他设备网络都正常，没必要因为一个 Quest 把所有设备的 DNS 都绑到 OpenClash 上。

后来在主路由上抓包时发现一个有用的细节：Quest 向主路由的 IPv6 地址发送 DNS 请求时，数据包虽然经过 Mesh 节点，但主路由在 br-lan 接口上依然能看到 Quest 自己的源 MAC 地址。既然主路由能识别出这台设备，就可以只处理 Quest 发来的 DNS 请求，不影响其他设备。

## 只给 Quest 转发 DNS

最终采用的办法不复杂。我在主路由上额外启动了一个 dnsmasq 实例，让它监听主路由的 IPv6 链路本地地址，端口使用 1053，上游 DNS 指向旁路由：

```text
192.168.28.2:53
```

原来负责全家 DNS 的 dnsmasq 不做修改，继续正常工作。然后通过防火墙规则筛选符合以下条件的数据包：

1. 从 br-lan 接口进入。
2. 源 MAC 地址是 Quest 3。
3. 目标地址是主路由自己的 IPv6 DNS 地址。
4. 目标端口是 TCP 或 UDP 53。

只有同时满足这些条件的 DNS 请求，才会被转发到本机新建的 1053 端口。我没有修改 Quest 的 IPv6 DNS 地址，也没有修改它的 IPv6 默认网关，只是把 DNS 请求在主路由内部转了一下。

整体过程大概是这样：

```text
Quest 3
  │
  │ IPv6 DNS 请求 :53
  ▼
主路由
  │
  ├── 识别 Quest 的 MAC 地址
  │
  └── 转发到本机 :1053
          │
          │ IPv4 DNS :53
          ▼
      旁路由 .2
          │
          ▼
       OpenClash


其他设备
  │
  └── DNS :53 → 主路由原有 DNS 服务
```

新开的 1053 端口也做了访问限制，只允许经过这条规则转发过来的请求使用。这样 Quest 的网络设置页面里，IPv6 DNS 依然显示主路由，这很正常：它发出请求后，主路由会帮它转交给旁路由。Quest 的 IPv6 公网流量仍然按原来的路由走，不会因为这条 DNS 规则改变。

配置完成后，我没有马上永久启用，而是先做了一次三分钟临时测试。为了避免规则写错导致家里断网，我提前备份了防火墙配置，并设置了自动回滚。测试结果比较理想：

- Quest 通过 IPv6 发送 DNS 请求，拿到的是 OpenClash 的 Fake-IP。
- 普通电脑向同一个 IPv6 DNS 地址查询，拿到的仍然是真实公网 IP。
- 三分钟后临时规则自动撤销，Quest 再次查询时，恢复成主路由原来的公网 DNS 结果。

这次测试确认了修改只影响 Quest，没有把全家的 DNS 一起改掉。

## HTTPS 测试的坑

DNS 正常后，HTTPS 还是不通。第一轮测试时，Quest 访问百度的 HTTP 探测能返回 200，但访问国外网站时始终没有拿到可以确认的应用层响应。一开始我以为是 OpenClash 或代理节点的问题，仔细检查后发现，之前使用的 HTTPS 测试方式本身就不太可靠。

当时我想通过 ADB 把 TLS 握手数据发送到 Quest，再把返回的数据读回来，使用的是 Windows 上的：

```bash
adb shell -T cat
```

为了确认这条通道有没有问题，我先准备了一组已知的二进制数据进行测试。结果发送了 256 字节，最后只收回 27 字节，而且内容还发生了变化。这说明这条通道不能可靠传输原始二进制数据。之前 HTTPS 测试失败，很可能是测试工具自己出了问题，而不是代理不通。

后来换成 ADB 服务提供的原始二进制通道重新测试，结果终于正常了：

- Quest 通过 Fake-IP 访问百度 HTTPS，返回 200。
- 访问 Google 的 `/generate_204`，返回 204。

我又重新做了一次临时 DNS 转发测试，先让 Quest 查询到 Google 对应的 Fake-IP，再直接从头显发起 HTTPS 请求，同样拿到了 204。至此，DNS 转发和实际 HTTPS 连接都正常了。

旁路由日志里之前确实出现过 Quest 连接代理节点超时或被拒绝的记录。这是另一个问题：节点连接偶尔失败和 DNS 绕过并不冲突。

## 持久化和回滚

确认测试没问题后，我才把这套配置正式保留下来。主路由的 `/etc` 实际上在内存里，单纯把脚本放在那里，重启后不能保证还在。所以我把新增的 dnsmasq 服务放到了主路由的持久存储 `/data` 下面，同时在防火墙配置里增加了一个独立启动项。

我检查了持久化配置，也手动调用了启动入口，提交配置后又重新测试了 Quest 的 DNS 和 HTTPS。这次没有为了测试强制重启主路由，所以配置持久化和启动入口已经验证，但真正重启后的自动恢复还没实测，准备留到下次维护时确认。我也准备了回滚脚本，需要恢复时可以停止新增服务，并删除对应的防火墙规则和启动项。

目前普通电脑依旧能使用原来的公网 DNS，NAS 也能正常访问。

测试电脑里还保留着几组旧的 IPv6 地址，默认连接时选中了已经更换的前缀，导致 HTTPS 超时。即使把这次的临时规则撤掉，问题依然存在；指定当前前缀的地址则可以正常访问。这台电脑的 IPv6 默认连接还需要后续重新检查，和这次 Quest DNS 修改无关。

这套方案也有范围限制：目前只处理 Quest 发往主路由的普通 DNS 请求，也就是 TCP/UDP 53 端口。如果某些应用自己使用 DoH、写死了其他 DNS 服务器，或者直接通过 IPv6 访问公网，这些都不在规则处理范围内。以后 Quest 如果更换了 Wi-Fi MAC 地址，也需要同步修改防火墙匹配条件。这次主要验证了 DNS 转发以及国内外 HTTPS 访问，没有重新测试之前文章里提到的商店大文件下载。

折腾完这一圈，我觉得最有价值的收获不是增加了几条防火墙规则，而是终于弄明白了 Quest 为什么会绕过旁路由。以前遇到代理问题，我可能第一反应就是检查 OpenClash 规则、DNS 配置和代理节点。但这次问题甚至还没到 OpenClash，DNS 请求就已经被主路由接走了。

以后再遇到类似问题，我会先看设备实际拿到了什么 DNS、默认网关分别指向哪里，再检查 IPv4 和 IPv6 流量究竟从哪台路由出去。先把网络路径搞清楚，很多问题就没那么复杂了。

至少这次，我终于不用为了 Quest 3 把全家的 IPv6 都关掉了。
